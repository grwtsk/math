# Proofs, observations, receipts and certificates

| Object | Role | Limit |
|---|---|---|
| Observation | Reports inspected data or a checker outcome | May be incomplete, stale or erroneous |
| Receipt | Binds an actual action/outcome to exact inputs and environment | Does not make a proposition true |
| Proof | Derives an exact proposition from its premises | Proves only that proposition under those premises |
| Scoped certificate | Packages evidence accepted by a specified sound checker | Requires that checker and its trust assumptions |
| Authorization | Permits a particular operational effect | Does not supply mathematical premises |
| Documentation | Explains and indexes these objects | Does not strengthen their evidence |

Receipts inform downstream formalization by exposing usable declarations, missing hypotheses and failed routes. A proof still imports a declaration or supplies a proof term; it cannot substitute “a successful run was reported” for a mathematical hypothesis.

Track mathematical statement, source identity, checking evidence, integration and publication separately. A retained successful check of an earlier source remains historical when the current source differs. A relocated module needs affected integration replay; relocation alone does not erase or renew its proof evidence.

Unknown lineage remains unknown. Failed controls and attribution corrections remain visible. There is no universal promotion from a finite test corpus to a universal implementation theorem.
